# Upgrading to 2.0

This page lists what changes for you when you move from SLayer 1.x to 2.0: first every breaking change, grouped by
where you meet it, then what 2.0 deprecates and 3.0 will remove. Each entry shows what you wrote on 1.x and what to
write on 2.0.

Stored datasets, queries, memories and datasources upgrade in memory on every load, and a load never rewrites them;
`slayer storage upgrade` stores them in the current format (see [Stored documents](#stored-documents)). Nothing below
asks you to edit stored documents by hand unless it says so.

## Part 1: breaking changes

### Expressions and filters

Every text position of a query (metrics, filters, computed dimensions, `order`) and of a dataset (field `sql`,
metrics, dataset filters) reads one SQL-like grammar.

**The colon spellings are gone.** `amount:sum`, `*:count`, `amount:last(created_at)` and the bucket `created_at:month`
are refused with an error naming the replacement, in queries, dataset metrics, `order` keys, memory `linked_entities`
and `recommend_population` items. Stored text is rewritten on load and returns the same rows and result keys.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "dimensions": ["created_at:month"], "measures": ["amount:sum", "*:count"], "order": [{"column": "amount:sum", "direction": "desc"}]}
```

```json
{"population": "orders", "dimensions": ["date_trunc('month', orders.created_at)"], "metrics": ["sum(orders.amount)", "count(orders.*)"], "order": [{"field": "sum(orders.amount)", "direction": "desc"}]}
```

**`year`, `quarter`, `month`, `week`, `day`, `hour`, `minute` and `second` extract an integer.** `month(created_at)`
was the month bucket on 1.x; it is now 1 to 12, under the result key `date_part_month_created_at`. Write the bucket
as `date_trunc('month', created_at)`, which gives the 1.x rows and key. The SQL facades read `MONTH(col)` the same
way. An extraction compared with a date-shaped string (`month(created_at) = '2025-03'`) is refused, and
`year(created_at) = 2025`, which matched nothing on 1.x, now matches.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "dimensions": ["month(created_at)"], "measures": ["sum(amount)"]}
```

```json
{"population": "orders", "dimensions": ["date_trunc('month', orders.created_at)"], "metrics": ["sum(orders.amount)"]}
```

**Granularity names are not functions.** `week_sunday(created_at)` and a custom granularity's call form, such as
`fiscal_year(created_at)`, are refused; write `date_trunc('week_sunday', created_at)`. A string entry in
`time_dimensions` must be a `date_trunc` call, and a time transform such as `cumsum` needs a `date_trunc` dimension,
not an extraction.

**Unquoted names match in any case.** `SUM(Amount)` reads field `amount`, and `ORDERS` names dataset `orders`;
double-quote a name to match it exactly. A query whose result names differ only in case (`total` and `Total`) is
refused.

**Double quotes name a field.** Strings take single quotes. When a field of the quoted name exists, the comparison
silently runs against that field; otherwise it fails with an error saying strings use single quotes.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "filters": ["status = \"paid\""]}
```

```json
{"population": "orders", "filter": ["orders.status = 'paid'"]}
```

**Backslash is an ordinary character in a string.** Escape a quote by doubling it. On 1.x, `'O''Brien'` silently
became `'OBrien'` and `'C:\temp'` held a tab.

<!-- docs-guard: skip -->
```json
{"source_model": "people", "filters": ["name = 'O\\'Brien'"]}
```

```json
{"population": "people", "filter": ["people.name = 'O''Brien'"]}
```

**`--` starts a comment** that runs to the end of the line. `amount --1` is now `amount`; write `amount - -1`.

**`|` is not an operator.** Concatenate with `||` or `concat()`.

<!-- docs-guard: skip -->
```json
{"source_model": "people", "dimensions": [{"expression": "first | ' ' | last", "name": "full"}]}
```

```json
{"population": "people", "dimensions": [{"field": "people.first || ' ' || people.last", "alias": "full"}]}
```

**Variables supply values only.** A `{var}` is a value inside quotes, a bare number or boolean, or a whole `IN` list.
Field names, conditions and function names go in the query text itself.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "filters": ["{col} = 'paid'"], "variables": {"col": "status"}}
```

```json
{"population": "orders", "filter": ["orders.status = '{s}'"], "variables": {"s": "paid"}}
```

**Bare `current_date` and `current_timestamp` are the database clock**, even on a dataset with a field of that name.
Double-quote the field to reach it: `d < "current_date"`.

**One LIKE pattern language on every database.** `%` and `_` are the only wildcards, `\` escapes them, `[` is a
literal character (it was a character class on SQL Server), and LIKE is case-sensitive on SQLite as elsewhere. Use
`ILIKE` for a case-insensitive match.

<!-- docs-guard: skip -->
```json
{"source_model": "stores", "filters": ["name LIKE 'a%'"]}
```

```json
{"population": "stores", "filter": ["stores.name ILIKE 'a%'"]}
```

**`greatest` and `least` skip NULL arguments on MySQL, BigQuery and ClickHouse**, as they already did elsewhere. Spell
out the NULL test if you relied on a NULL result:
`CASE WHEN a IS NULL OR b IS NULL THEN NULL ELSE greatest(a, b) END`.

**Text compared with a number compares as numbers.** Text that is not a number reads as NULL. Redshift, Databricks,
Spark and Oracle refuse this comparison. Compare with a string to keep text ordering, or `CAST` explicitly.

<!-- docs-guard: skip -->
```json
{"source_model": "codes", "filters": ["code > 5"]}
```

```json
{"population": "codes", "filter": ["CAST(codes.code AS DOUBLE) > 5"]}
```

**`ln`, `log`, `log10`, `log2`, `sqrt` and `pow` return NULL outside their domain** instead of failing (SQLite) or
returning `-inf` / `NaN` (DuckDB); a literal out-of-domain call such as `ln(0)` is refused. Wrap the call in
`coalesce` for a fallback value.

**Every branch of `CASE`, `iif`, `coalesce` and `ifnull` has one type, on every database.** 1.x already refused a
plain mixed-type `CASE`; it now also refuses branches typed by arithmetic, `||`, `concat` or a joined field, a `CASE`
inside an aggregate, and mixed `coalesce` / `ifnull`. `CAST` the odd branch.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "dimensions": [{"expression": "coalesce(amount, 'n/a')", "name": "shown"}]}
```

```json
{"population": "orders", "dimensions": [{"field": "coalesce(CAST(orders.amount AS TEXT), 'n/a')", "alias": "shown"}]}
```

**`first` and `last` without a ranking key, grouped by a computed date or timestamp, rank by that expression.** 1.x
ranked by the first time field the expression read. The expression has one value per group, so pass the ranking key
explicitly.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "dimensions": [{"expression": "coalesce(shipped_at, created_at)", "name": "effective"}], "measures": ["last(amount)"]}
```

```json
{"population": "orders", "dimensions": [{"field": "coalesce(orders.shipped_at, orders.created_at)", "alias": "effective"}], "metrics": ["last(orders.amount, orders.shipped_at)"]}
```

**`first` and `last` without a ranking key read the query's dimensions, whatever their `partition_by=`, `window=`,
`time_shift` or nesting.** 1.x ranked a partitioned, windowed, shifted, nested or cross-model one by the dimensions its
own grain kept, and a query whose only time field was in a filter by that field; pass the ranking key explicitly to keep
the old value. When that dimension is reached across a fanning or unproven relationship, the query is now refused
with the ranked-input safety error, as an unpartitioned `first` / `last` already was; pass the ranking key explicitly.

**`first` and `last` never pick a row whose ranking key is NULL**, on every database, and a group whose keys are all
NULL gives NULL. 1.x could pick such a row: `first` on SQLite, `last` on Postgres.

**A root-dataset prefix is resolved, not stripped from the text.** Text inside quotes stays as written (1.x turned
`'see orders.x'` into `'see x'`), a path such as `orders.orders.status` through a relationship named like the root reaches
that relationship, and a stage name works as a qualifier in a later stage.

**A date compared with a timestamp is its midnight.** `created_at <= '2024-12-31'` stops at `2024-12-31 00:00:00`, as
in SQL; 1.x read the whole day, so `<=`, `>`, `=`, `!=` and `BETWEEN` against a TIMESTAMP now match fewer or other
rows. A DATE field, `>=` and `<` are unchanged. The whole day is `created_at in '2024-12-31'`, and `date_range` bounds
still cover whole days. A query or save that compares this way carries a `date_only_midnight` warning naming the
whole-day spelling, until SLayer 3.0. Stored queries, memories and dataset metrics and field filters are rewritten on
load to the whole-day spelling and return their 1.x rows; a comparison whose field cannot be resolved is left as
written and logged. A variable's stored default is not rewritten: a date it binds into such a comparison is midnight,
and the warning names the variable.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "filters": ["created_at <= '2024-12-31'"], "measures": ["count(*)"]}
```

```json
{"population": "orders", "filter": ["orders.created_at < '2025-01-01'"], "metrics": ["count(orders.*)"]}
```

**On SQLite, `CAST(x AS TIMESTAMP)` is a timestamp.** It returned the year (`2024`); it now converts as `TRY_CAST`
does, NULL for a value that is not a date or date-time. A cast to `TIME`, to a zoned timestamp or to a timestamp with
a precision is refused there.

**On SQL Server, `CAST(x AS TIMESTAMP)` is a `DATETIME2`.** It rendered SQL Server's `TIMESTAMP`, a row version. On
ClickHouse a cast to `TIME` is refused at plan time; it read NULL.

**A number cast to `BOOLEAN` is true when it is not zero, on every database.** On SQLite `CAST(5 AS BOOLEAN)` was `5`
and `CAST('true' AS BOOLEAN)` was `0`; they are now `1`, and text that is no boolean word is NULL. On ClickHouse the
result is a `Bool`; it was the integer `1` or `0`.

**A fraction cast to an integer type rounds half away from zero.** `CAST(2.5 AS INT)` was `2` on SQLite, SQL Server and
ClickHouse; it is `3` everywhere, and `CAST(-2.5 AS INT)` is `-3`.

**A `DECIMAL` cast keeps its scale, and an omitted one is 0.** `CAST(12.345 AS DECIMAL(10,2))` was `12.345` on SQLite;
it is `12.35`. A bare `DECIMAL` / `NUMERIC` is `DECIMAL(38, 0)` and `DECIMAL(p)` is `DECIMAL(p, 0)`: `CAST(12.5 AS
DECIMAL)` was `12.5` on DuckDB, SQLite and Postgres and is `13`. Write the scale you want (`DECIMAL(10, 2)`).
Numeric text with an exponent (`'9007199254740993e0'`) keeps every digit; on Trino and SQL Server it was read through a
double.

**`VARCHAR(n)` keeps the first `n` characters.** `CAST('abcdef' AS VARCHAR(3))` was `'abcdef'` on SQLite and refused on
DuckDB; it is `'abc'` everywhere.

**`TRY_CAST` of a fraction to an integer rounds.** `TRY_CAST(1.5 AS INT)` was NULL; it is `2`, as `CAST` gives, and a
JSON number does the same (`json_value(doc, '$.v' RETURNING INT)` over `{"v": 1.5}` is `2`). `TRY_CAST(5 AS BOOLEAN)`
was NULL and is true. `INT` is 32-bit everywhere: `TRY_CAST('3000000000' AS INT)` is NULL on SQLite, MySQL,
Snowflake and BigQuery too; use `BIGINT`.

**`round(x, d)` with a negative `d` rounds left of the decimal point on SQLite.** `round(1250, -2)` was `1250` there;
it is `1300`, as on every other database. On ClickHouse a number literal's tie rounds away from zero: `round(2.5, 0)`
was `2` and is `3`.

**`round(x, d)` needs whole-number digits.** `round(x, 1.5)` gave a database-dependent answer (`12.3` on SQLite, an
error on DuckDB) and is now refused at plan time; write a whole number, such as `round(x, 2)`. An integer field
(`round(x, n)`) is now accepted.

**A field's number function over a TEXT column is refused when saved.** A field whose `expression` is `abs(status)` over
a TEXT `status` saved and then ran each database's own coercion (`0.0` on SQLite, an error on DuckDB); it is now
refused when saved, and a stored one when a query reads it, naming `TRY_CAST`: write `abs(TRY_CAST(status AS DOUBLE))`.

**`median` and `percentile` are exact on Trino and answer on MySQL, SQL Server and BigQuery.** Trino's were
approximate (`APPROX_PERCENTILE`); the other three raised.

**A field's expression may not call `AGG`.** Saving a field whose `expression` is `AGG(amount)` is refused (`AGG` is
for metrics: `AGG(dataset.metric)` in a model-scoped metric). A stored one is rewritten on load to its argument
(`AGG(amount) + 1` becomes `amount + 1`), returning the same rows, with a logged warning naming the field.

**The strict binding admits a scalar only at an argument count Ossie defines.** Under `conformance="ossie-l3"`, a
filter calling `ROUND(x)`, `TRUNC(x)`, `LOG(x)`, `SUBSTRING(s, start)` or a regex function with flags was admitted and
is now `E_INVALID_QUERY`; write `ROUND(x, 0)`, `LOG(10, x)` or `SUBSTRING(s, start, length)`. `PERCENTILE_DISC` and
`APPROX_PERCENTILE` are `E_INVALID_QUERY` too, until SLayer evaluates them. Native queries are unchanged.

### Aggregates across a to-many relationship

**Omitting `to_many_handling` now associates.** An aggregate sliced by a dimension its dataset does not determine, such
as `sum(customers.spend)` by `orders.status`, gives in each cell the total over the distinct customers reaching it,
with an `associated` warning; the cells overlap, so they need not add up to the total. 1.x repeated the grand total
in every cell with a `broadcast` warning. To keep the 1.x values, give the aggregate `partition_by=` with the
dimensions its dataset determines (`[]` for the grand total):

```json
{"population": "orders", "dimensions": ["orders.status"], "metrics": ["sum(customers.spend, partition_by=[])"]}
```

`to_many_handling: "broadcast"` still returns the 1.x values in 2.x, but is deprecated: see
[Part 2](#part-2-deprecated-in-20-removed-in-30).

**Queries stored by 1.x associate too.** 1.x wrote `to_many_handling: "broadcast"` into every query it stored, and 2.0
drops that value on load. Add `partition_by=` to the aggregates of each stored query that must keep its 1.x values.

**An explicit `"associate"` now reaches a nested aggregate's inner**: `sum(sum(customers.spend))` associates instead of
broadcasting. `first`, `last` and `window=` aggregates associate too.

**`"error"` (and the deprecated `"broadcast"`) now cover local `first`, `last` and `window=` aggregates.** Grouped by a
dimension their dataset does not determine, they are refused (or broadcast) like every other aggregate. A window whose
time axis fans from its dataset (customers' `sum(spend, window='1y')` by month of `orders.ordered_at`) is a typed error
in both modes; omit `to_many_handling` or set `"associate"` to count each customer once per bucket. In 1.x they were computed
over the joined rows, which counted a windowed value once per related row: customers' `sum(spend, window='1y')` by
`orders.status` counted each customer once per order.

**In Python, `SlayerQuery.to_many_handling` is `None` when omitted**, not `"broadcast"`.

**An expression combining fields no single dataset determines is refused** as a dimension, time dimension or order
key, in every `to_many_handling` mode: `orders.amount * returns.amount` from `customers` pairs every order of a customer
with every return of that customer, and is now an `UnsafeRelationshipInputError` naming both fields and their hops.
Aggregate one side to a grain the other's dataset determines
(`orders.amount * sum(returns.amount, partition_by=[customers.customer_id])`), or group by each field as its own
dimension. A filter combining them still restricts by association.

**An expression reads as a field of its home dataset**: when it combines a to-many child's field with a parent's,
a population row without a child row reads NULL, as the child's own field does —
`coalesce(orders.shipped_at, customers.signup_ts)` is NULL for a customer without orders, where 1.x gave the signup
date.

### Declared cardinality is not trusted

**A declared `many_to_one` no longer changes a value.** 1.x joined a to-one hop directly, so a duplicated `customers`
row counted its orders twice in `orders.total_revenue` by `customers.region`. 2.0 counts each order once in each group
it matches, as Ossie defines. It reads the target through a `SELECT DISTINCT` of the join keys and grouped values,
unless the hop is [trusted](../concepts/datasets.md#trusted-relationships). On data that satisfies the declarations,
the values are unchanged.

**Models, saved queries and memories stored by 1.x keep their results.** On load every stored relationship gets
`trusted: true`. Stored semantic-model documents and fresh models are not upgraded. To keep the direct join on a fresh
model, set `trusted: true` on the relationship. Re-ingesting a database that enforces its keys records
`enforced_keys`, which also restores the direct join.

**An aggregate input across an untrusted hop** (`wsum(orders.amount, weight=customers.weight)`) reads one matching
value per order. Under `to_many_handling: "error"` it is refused; mark the relationship trusted or record an enforced
key to accept it.

### Lists

**`length(list)` counts distinct non-NULL elements**: `["go", "sql", "go"]` has length 2. Count elements with
repeats with `count(list.*)`.

```json
{"population": "contractors", "dimensions": ["contractors.id"], "metrics": [{"metric": "count(contractors.skills.*)", "alias": "n"}]}
```

**A list whose `element_type` is `UNKNOWN` no longer has `length`**; only NULL tests and `count` remain. Declare the
field's `element_type` to read its elements.

### Datasets and datasources

**A field is defined by `expression`, and a bare name in it reads the source column.** In a field's `expression` or
`filter` and a dataset's `filters`, a bare name or `source.x` reads the dataset's source column and a path (`orders.gross`,
`customers.region`) reads a field; 1.x read a bare name as a sibling field whenever one existed. The `expression` is
Ossie's `{sql, dialects}` object or a string standing for its portable `sql`: the entry for the datasource's own
dialect runs, else the portable `sql`, read by SLayer's Mode B grammar with Ossie's meaning. Stored datasets convert
on load so their results do not change: a field's `sql` naming one column becomes the shorthand, other `sql` becomes the
entry for the datasource's dialect with each sibling it read written as a path, and a filter's bare sibling names
become paths. A dataset whose store holds no datasource config keeps its `sql` until the dialect is known. Cube, dbt
and Ossie imports now read a physical column whose name a field has taken, and import self-named transforms
(`status: UPPER(status)`).

**In a dataset metric's `expression`, `source.x` reads a source column** unless the dataset declares a field named
`source`; a stored metric that used `source` as a relationship path is rewritten to the target dataset's name, or does
not load when that name is not a unique hop.

**A datasource custom granularity named like a new library function is renamed** to `<name>_granularity` (`left`
becomes `left_granularity`, recording `renamed_from: left`), with every reference in a document written before the
rename read under the new name on every load; `slayer storage upgrade` stores the rename. Queries you send use
the new name. The newly reserved names are `acos`, `ascii`, `asin`, `atan`, `atan2`, `cbrt`, `chr`, `concat_ws`,
`cos`, `date_trunc`, `div`, `ends_with`, `ilike`, `json_extract`, `json_extract_path_text`, `json_extract_scalar`,
`json_value`, `jsonb_extract_path_text`, `left`, `lpad`, `pi`, `regexp_extract`, `regexp_like`, `regexp_replace`,
`repeat`, `reverse`, `right`, `rpad`, `sin`, `split_part`, `starts_with`, `strpos` and `tan`. Ossie's `charindex`, `degrees`,
`endswith`, `if`, `nullifzero`, `nvl`, `nvl2`, `radians`, `regexp_count`, `startswith`, `to_date`, `to_timestamp`,
`truncate` and `zeroifnull` are reserved too.

**A custom aggregation named like one of these functions keeps working inside its dataset**, and every save, load and
query response through it carries a `library_name_shadow` warning. Rename the aggregation to silence it.

**`agg` is reserved.** A dataset aggregation named `agg` is renamed on load to `agg_aggregation`, with the dataset's own
calls rewritten; call `agg_aggregation(amount)` in queries, since `agg(amount)` is refused.

**Names that differ only in case cannot be saved together.** Saving a dataset whose names differ only in case (fields
`amount` and `Amount`) is refused; a stored dataset that already has them keeps working with a `name_collision`
warning. Ingestion names the later of two physical columns that differ only in case `<name>_2`:
Postgres columns `amount` and `"Amount"` become `amount` and `Amount_2` (1.x kept `Amount`, and `Amount` now reads
`amount`).

**Postgres sets the statement timeout once per connection** instead of in a transaction around every query. A
datasource behind a transaction-mode pooler (such as PgBouncer in transaction mode) must opt back in:

```yaml
name: warehouse
type: postgres
host: pgbouncer.internal
transaction_pooler: true
```

**Schema drift checks a filtered field's source column.** A field with a `filter` over a vanished column is dropped
with the metrics reading it (1.x kept it), and a re-typed column reports a re-type finding for it.

### Stored documents

**A load never writes.** Migrations, repairs, conversions and the granularity rename run in memory on every load; 1.x
rewrote an old document on its first load. A save stores the upgraded form, and so does `slayer storage upgrade`
(`--dry-run` prints each document's difference; see [the CLI reference](../reference/cli.md#slayer-storage)). Until
then each such document loads with one `stored_upgrade_needed` warning per store. A 1.x release still reads a store
2.0 has only loaded.

```bash
slayer storage upgrade --dry-run
slayer storage upgrade
```

A document whose field `sql` waits for its datasource's dialect, one below version 8 whose datasource cannot be
reached for type refinement, one that fails to load, and one changed while the command ran are reported and left as
they are, and the command exits 1. Pass `--datasource-type NAME=TYPE` for a datasource the store holds no config for.

For dataset documents SLayer does not own, `slayer.storage.upgrade.upgrade_datasets` returns them in the stored
format without opening a store:

```python
from slayer.storage.upgrade import upgrade_datasets

result = upgrade_datasets(documents=[orders_doc, customers_doc], datasource_type="duckdb")
upgraded, refused = result.documents, result.refused  # each refusal has .name and .reason
```

### Query JSON

**A serialized time dimension carries its field as a dotted string.** The object form is still accepted as input.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "time_dimensions": [{"dimension": {"name": "created_at", "model": "customers"}, "granularity": "month"}]}
```

```json
{"population": "orders", "time_dimensions": [{"field": "customers.created_at", "granularity": "month"}]}
```

**A stage keeps the relationships of the keys it passes through.** 1.x read a later stage's dataset reached through
such a key as unrelated (broadcast, with a warning); it is now joined, so those values change. A dotted reference
into a stage that no relationship resolves gets the error a stored dataset gives, suggesting the flat field name.
A stage reading a sibling only through an expression no longer depends on the stages' names, and routing never
passes through a sibling the stage does not name.

```json
[
  {"name": "per_customer", "population": "orders", "dimensions": ["customer_id"], "metrics": [{"metric": "sum(amount)", "alias": "revenue"}]},
  {"population": "per_customer", "dimensions": ["customers.region"], "metrics": [{"metric": "sum(revenue)", "alias": "total"}]}
]
```

### Result values

REST, MCP and the CLI encode result values one way:

| Value | 1.x | 2.0 |
| -- | -- | -- |
| Decimal (JSON) | `"12.30"` | `12.30` |
| NaN, ±Infinity (MCP and CLI JSON) | `NaN`, `Infinity` (invalid JSON) | `null` |
| Timestamp (MCP and CLI JSON) | `"2024-01-02 03:04:05.500000"` | `"2024-01-02T03:04:05.500000"` |
| Bytes | `"b'\\xde\\xad'"` (MCP, CLI); garbled (REST) | `"\\xdead"` |
| Interval (MCP and CLI) | `"1 day, 2:00:00"` | `"P1DT2H"` |
| NULL (MCP csv) | `None` | empty cell |
| Boolean (csv, markdown, table) | `True` / `False` | `true` / `false` |
| NaN, ±Infinity (csv, markdown, table) | `nan` / `inf` | `NaN` / `Infinity` |

**A time bucket has one type on every database**: a day-or-coarser bucket of a DATE is a date (DuckDB and Postgres
returned a timestamp), any other bucket a timestamp, on SQLite `YYYY-MM-DD HH:MM:SS` text even at `day` and coarser
(1.x returned `YYYY-MM-DD`). See [Time](../concepts/time.md#time-buckets).

**A plain facade `SELECT` returns every record.** Over the PostgreSQL wire facade and Flight SQL, a `SELECT` without
an aggregate, `GROUP BY` or `DISTINCT` returned distinct rows on 1.x; it now returns one row per record. Add
`DISTINCT` for the old result: `SELECT DISTINCT status FROM orders`. List, bytes and interval columns, which 1.x
refused to select, return as text.

### Qualified references

**Every reference starts at a dataset.** The first segment of a dotted reference names a dataset (or a stage of the
same query list), and the rest is an explicit route from it. The engine reaches that dataset from the population by
its only to-one path, else its only route. A 1.x query read every reference from its population, so a query that
names its population keeps working: see [Root-relative references](#root-relative-references).

**Result keys never carry the population.** A key is the reference as written, its route spelled canonically; an
alias is the key itself; an unaliased expression keys by its references' common dataset, or by its text alone when
they share none. Stage column names are unchanged.

| Entry, population `customers` | 1.x key | 2.0 key |
| -- | -- | -- |
| `sum(orders.amount)` | `customers.orders.amount_sum` | `orders.amount_sum` |
| `count(orders.*)` | `customers.orders._count` | `orders._count` |
| `{"metric": "sum(orders.amount)", "alias": "revenue"}` | `customers.revenue` | `revenue` |
| `regions.name`, routed through `customers` | `customers.regions.name` | `regions.name` |

**A direct relationship has no precedence.** When two paths from the population to a dataset are to-one, a reference
starting at that dataset is refused naming each explicit path, even when one is a direct relationship. Write the one
you mean:

```json
{"population": "orders", "dimensions": ["orders.customers.region"], "metrics": ["count(orders.*)"]}
```

**Ossie precedence.** A route or dimension anchor Ossie determines uniquely — a sole path of declared many-to-one
steps, a sole dimension dataset reaching every other along them — is taken over every other candidate. A route Ossie
settles is no longer refused as ambiguous; on a model where a relationship read backwards was provably to-one, a query
without `population` that depends on its dimension anchor (dimension-only queries, raw rows, the reported
`population`) may now read from Ossie's anchor instead of the one with fewer hops. Saved queries keep their stored
anchors.

**An alias may equal a field name.** A user-written alias of a dimension or metric no longer collides with a field of
the same name (1.x's `MeasureNameCollidesWithColumnError` is gone): fields are always qualified and aliases bare, so a bare
`order` key such an alias holds names its column, and `orders.amount` names the field.

**A directed cycle reads its to-one path.** Over `x → y → z → x`, all many-to-one, `sum(z.amount)` from `x` read the
`z` rows referencing each `x` on 1.x; it now sums the `z` row reached through `x → y → z`. The response carries a
`changed_reference` warning naming the reference, the path it takes and the spelling of the old path, `x.z.amount`.
The warning is removed in 3.0.

**`count(*)` without a population is refused**, with or without dimensions. Write `count(<dataset>.*)`, or name the
population.

**A bare name is a metric**: an alias of the query. Any other bare name in a query without a population is refused
with an `UnknownMetricError` suggesting each qualified field and metric of that name.

**`recommend_population`** takes qualified items: `count(orders.*)` is an attachment on `orders`; a bare name or
`count(*)` is refused with the qualified spellings.

Stored queries and memories upgrade themselves on load to the qualified spelling with their old meaning: a reference
whose old path the new reading would not take is spelled as its explicit route from the population, and an unaliased
expression whose references share no dataset gets its old column name as its alias. A bare name keeps its 1.x reading
by position: inside an entry, the population's field, then its metric, then another entry's alias; in a filter or
order, the population's field, then an alias, then the population's metric. A stored query whose old path has
no explicit spelling (it crossed one of two unnamed parallel relationships) no longer loads; name the relationships
and save it again. A stored memory with no population (or the `time_spine` one) upgrades in the datasource its
entities name, else the only datasource holding a stored dataset; otherwise it no longer loads, so add a population and save it again.

### Root-less queries list the row supply

**Dimension values no metric reaches disappear.** A query without `population` used to list every value of its
dimensions' dataset. It now lists the values each metric's rows reach (see [Population](../concepts/queries.md#population)).

<!-- doc-check: not-a-query -->
```json
{"dimensions": ["customers.region"], "metrics": ["sum(orders.amount)"]}
```

| 1.x | 2.0 |
| -- | -- |
| EAST 350 · WEST 300 · NORTH NULL | EAST 350 · WEST 300 |

To keep NORTH, add a metric from the dimension's dataset (`count(customers.*)`), or name `"population": "customers"`.

**Orders with no customer land in a NULL row.** On 1.x they were dropped without a warning. The same query over data
with an order of a missing customer returns EAST 350 · WEST 300 · NULL 70.

**Filters no longer move the population.** A field filter restricts each metric's rows and never changes which dataset
the rows come from, so adding one never adds a row or renames a key — except a computed dimension read from an
aggregate over the filtered rows. On 1.x, `orders.amount > 60` added to the query
above made `orders` the population.

**A query with metrics and no dimensions returns one row.** `{"metrics": ["sum(orders.amount)",
"count(tickets.*)"]}` used to fail with `PopulationInferenceError`; it now returns one row, with an `unrelated_dataset`
warning when the metrics' datasets have no relationship path between them.

**An aggregation reads its dimensions and filters from its own dataset.** Each one is routed from the aggregate's own
dataset by its only to-one path, also when `population` is named. Over `x → y → z → x`, `sum(z.amount)` grouped by
`x.v` from population `x` now sums each `z` row into the `x` it references. A dimension or filter starting at the
aggregate's own first segment goes back along the aggregate's path (`orders.status` beside
`sum(orders.billing_customer.spend)`). When the aggregate's dataset reaches another dataset by two to-one paths, a
reference starting there is refused naming both. Spell it through the aggregate's path instead
(`policy.party.code` beside `sum(policy.policy_amount.amount)`).

**An aggregation is read from its own anchor.** A named population no longer needs a route to a metric's dataset:
`orders.total_revenue` grouped by `regions.name` from population `regions` runs even when `regions` reaches `orders` by
two routes. A source whose references start at different datasets is read from the smallest dataset determining them;
when two datasets tie, the query is refused naming each spelling. Spell the source from one of them.

**A restricted population no longer narrows other datasets' metrics.** A population with dataset filters, hidden rows
or a filtering stage restricts a metric only where the metric's dataset reads it along its own paths. To restrict every
metric, filter the query instead of the population.

**Re-aggregations count their constituents' cells.** `avg(sum(orders.amount, partition_by=[orders.customer_id]))`
averages over the customers with an order, not over every customer of the population, so a customer with no order no
longer averages in as 0. To count every cell of a dataset, add a constituent from it at the same grain.

**Known gap.** Dimensions from datasets with no relationship path between them, beside a metric of one of them, are
refused with `UnrelatedDatasetError`.

**Saved stages pin the dimension anchor.** Saving a query-backed dataset now writes each inferred stage's dimension
anchor as `population` together with `population_inferred: true`, so its rows stay inferred. A stage saved by 1.x
with a pinned `population` keeps its anchored rows.

### Raw rows list each population row once

**A raw-row dimension the population does not determine is refused.** With `distinct_dimension_values: false`, every
dimension, time dimension and row-level order key must be reached from the population over provably to-one hops (see
[Raw rows](../concepts/queries.md#raw-rows-distinct_dimension_values)).

<!-- doc-check: not-a-query -->
```json
{"population": "customers", "distinct_dimension_values": false, "dimensions": ["orders.amount"]}
```

| 1.x | 2.0 |
| -- | -- |
| One row per order, a customer with two orders listed twice, plus a NULL row for a customer with none | `DistinctDimensionValuesError` naming `orders.amount` and the hop `orders` |

To list one row per order, name `"population": "orders"`; to keep the population, declare the hop's cardinality (or a
covering unique key) when it is really to-one, or drop the flag to list distinct values.

**The SQL facades advertise only joined dimensions a plain `SELECT` can list.** Over the Postgres wire and Arrow Flight,
`INFORMATION_SCHEMA.DIMENSIONS` and `SELECT *` leave out a joined dimension reached across a fanning or
unproven hop, and `SELECT parts.qty FROM things` fails instead of listing a `things` row per part. Select it
from its own table (`SELECT qty FROM parts`) or group by it (`SELECT parts.qty, COUNT(*) FROM things GROUP BY
parts.qty`).

### Transforms read their operand's cells; spine rows follow the row supply

**A transform's value never depends on the query's other rows.** Every transform, in every position, evaluates over
its operand's own cells and attaches its result to the rows; a row outside those cells reads NULL.

<!-- doc-check: not-a-query -->
```json
{"dimensions": ["customers.region"], "metrics": ["percent_rank(count(orders.*))", "returns.total_returns"]}
```

| 1.x | 2.0 |
| -- | -- |
| EAST 1 · WEST 0.5 · NORTH 0 | EAST 1 · WEST 0 · NORTH NULL |

`lag` / `lead` step over the operand's present cells, so a month only another metric supplies is a gap. With a named
`population`, a cell the operand lacks (an empty calendar month, a region without orders) reads NULL: a hand-made
calendar population is no longer a dense series — use the [time spine](../concepts/time.md#time-spine) for one.

**The rank family ranks its operand's cells.** `rank(sum(orders.amount, partition_by=orders.region), direction='desc')` grouped by
`orders.region` and `orders.city` used to rank the city rows; it now ranks the regions and repeats each rank on its
cities. A measure equal to a transform dimension reads that dimension's value.

**A time-ordered transform needs its axis in the operand grain everywhere.** `cumsum(sum(orders.amount,
partition_by=orders.region))` with a month time dimension is a `TimeAxisError` as a measure, filter or order key, as it
already was as a dimension; so are `time_shift`, `change` and `change_pct` over it, in every position. Add the time key
to `partition_by=`. A time-ordered transform over a nested `first` / `last`, which drops the axis, is refused in every
position too; apply it to the `first` / `last`'s operand instead.

**A NULL time bucket is a series of its own** on every database: a running total there is its own value, `lag` reads
NULL, and `first` / `last` skip it.

**Spine rows come from rows inside the frame.** Without `population`, a spine query lists every bucket for each group
with a measure value in a visible bucket; a group none of whose measures lands in the frame is no row (1.x showed it
with NULL in every bucket). A window or `time_shift` may still read facts before the frame, so its group stays when
that value lands in a visible bucket. Name `population` to keep the grid.

| query | 1.x | 2.0 |
| -- | -- | -- |
| spine month Jan–Mar × `customers.region`, `sum(orders.amount)` | N, S, E × 3 months | N, S × 3 months |

**A dataset without its own axis reaches the spine across a fanning hop.** `count(customers.*)` by spine month counted
every customer in every month; it now counts the customers with an order that month. When two such axes are equally
near (`customers.orders.order_date`, `customers.returns.return_date`), the query fails naming both: use a time
dimension on one of them. A dimension-only query can instead name `population` to keep the grid; a measure homed on
`customers` keeps the error.

| `slayer.osi.expression` | `slayer.importers.aggregates` |

Three of these are not drop-in:

- `parse_filter_expr` is deprecated: `slayer.core.syntax.parse_expr` reads SQL forms everywhere.
- `parse_formula(named_measures=...)` expanded saved metrics; `parse_expr` returns them as plain `Ref`s, and
  `AggCall` / `Arith` / `TransformCall` replace `ArithmeticField`, `TransformField`, `MixedArithmeticField`,
  `AggregatedMeasureRef` and `FieldSpec`. `TIME_TRANSFORMS` and `TIMELESS_TRANSFORMS` live in `slayer.core.enums`.
- `convert_expression` takes `sql_dialect=` in place of `percentile_unsupported=`.

```python
from slayer.core.syntax import parse_expr
from slayer.core.enums import TIME_TRANSFORMS

tree = parse_expr("status = 'x' AND amount <> 3")
```

**Loggers follow the module paths**: configure `slayer.live_schema.ingestion` and `slayer.database.client` instead of
`slayer.engine.ingestion` and `slayer.sql.client` (likewise `schema_drift`, `schema_scope`, `type_refinement`,
`engine_factory` and `sqlite_introspect`).

**Ingestion and drift validation take the SQL client.** `ingest_datasource()`, `ingest_datasource_report()`,
`ingest_datasource_idempotent()` and `validate_datasource()` require `client=`; `validate_datasource()` no longer
takes `sql_clients=`.

```python
datasets = await engine.ingest(ds)  # or ingest_datasource(ds, client=engine.client_for(ds))
dropped = await validate_datasource(datasource=ds, datasets=datasets, client=engine.client_for(ds))
```

**Converters read the database only through `collect_metadata`.** `DbtToSlayerConverter` no longer takes `sa_engine`,
and every parameter after `data_source` is keyword-only (`OsiToSlayerConverter` is gone: see
[Ossie documents](#ossie-documents)). Without `collect_metadata`,
`convert()` runs offline and reports what it skipped.

```python
converter = DbtToSlayerConverter(project, "warehouse", target_dialect="postgres")
await converter.collect_metadata(client=engine.client_for(ds))
result = converter.convert()
```

**Custom storage backends implement the current hooks.** 0.9.x-style subclasses are no longer adapted (the
`slayer.storage.legacy_backends` module is gone): implement `_save_datasource_impl` instead of overriding
`save_datasource`, and return `(memories, failed_rows)` from `_list_memories_rows`.

**Column types come from `get_result_column_types`.** `get_column_types_sync()`, `SlayerSQLClient.get_column_types()`,
`DelegatingSqlClient.get_column_types()` and `SlayerQueryEngine.get_column_types()` are gone, with
`type_categories`, `adapt_client` and `LegacyTypeCategories`. The replacements return `ResultColumnType` objects, not
category strings; a custom client implements `get_result_column_types(sql)`.

**EXPLAIN goes through the client's `explain`.** `SqlDialect.build_explain_sql()` is gone (use
`explain_statements()`), and a custom client implements `explain(statements: ExplainStatements)`. A
`DelegatingSqlClient` subclass that overrides only `execute` has its EXPLAIN served by the wrapped client, bypassing
its own `execute`; override `explain` too to route it.

**`create_mcp_server()` returns an mcp 2.x `MCPServer`**, not a `FastMCP`. `run()`, `sse_app()` and `list_tools()`
work as before; `call_tool(name, arguments, context=None)` returns a `CallToolResult` instead of a
`(content, structured)` tuple, and a failing tool raises `ToolError`.

```python
content, structured = await mcp.call_tool("query", {"query": query})   # 1.x
content = (await mcp.call_tool("query", {"query": query})).content      # 2.0
```

```python
class Gateway(DelegatingSqlClient):
    async def execute(self, sql):
        return await my_gateway.run(sql)

    async def explain(self, statements: ExplainStatements):
        return await my_gateway.run_explain(statements)
```

**The SQL client refuses session and transaction statements.** `execute("SET ...")`, `BEGIN`, `COMMIT`, `USE` and
the like raise `SessionStatementRefused`; SLayer manages sessions and transactions. Set statement timeouts and session
settings on the datasource.

**Dataset objects validate assignments.** Assigning an attribute on a dataset, field, metric, relationship,
aggregation, datasource or their nested objects runs the checks construction runs; a refused assignment raises
`ValidationError` (or the typed error construction raises) and leaves the object unchanged. Change attributes that are
checked together in one step with `assign(...)`. Saving a dataset or datasource re-validates it in full first, so an
in-place list edit that breaks it (`dataset.fields.append(...)` with a duplicate name) is refused before anything is
written.

```python
dataset.assign(sql="SELECT * FROM orders", sql_table=None)  # not two assignments
relationship.assign(from_columns=["a", "b"], to_columns=["c", "d"])
```

**`TimeDimension.field` is a `str`**, the dotted field path (`"orders.created_at"`), not a `ColumnRef`; a
`ColumnRef` passed as `dimension=` (or as an `OrderItem`'s `column=`) converts, deprecated.

```python
dataset, _, field = time_dimension.field.rpartition(".")
```

**Smaller removals:**

- `MemoryNotFoundError.identifier`: read `memory_id`.
- `SlayerQuery.strip_source_model_prefix()`, `query_variable_surfaces`,
  `slayer.core.time_spine.mentions_spine` and `ComputedDimension.substituted()`: root qualifiers and variables resolve
  when the query binds, so drop the calls.
- `substitute_variables(..., escape=...)`: the parameter is gone; pass `backslash_escapes=` only.
- `DatasetMetric.substituted(text)` requires `variables=`.
- `slayer.core.format.list_json_text`: use `encode_json(value)`.
- `apply_session_policy` and `policy_column_checks` take a parsed statement and an `SqlDialect` instead of SQL text
  and a dialect name.
- The dialect methods `statement_timeout_sql()` and `correlated_setting_sql()`, and
  `slayer.sql.client.build_sql_model_trial_query`.
- `SCALAR_FUNCTIONS` is no longer re-exported from `slayer.core.query` or `slayer.core.models`; import it from
  `slayer.core.keys`.
- `run_over_caller_engine`, `warn_deprecated(location=)` with `WarningLocation`, and `DriverFacts.bundled_non_default`.
- `AGG_REF_RE`, `split_agg_suffix` and `strip_agg_suffix` in `slayer.core.refs`: parse the text with
  `slayer.core.syntax.parse_expr`.

### Integrators reading SLayer objects

Code that reads SLayer's objects directly (model files, parse trees, drift results) keeps its 1.x calls through the
deprecated forms in [Integrator call forms](#integrator-call-forms). These values change and no deprecation carries
them:

- `DataType` values are Ossie's (`"Integer"`, `"Float"`, `"String"`, `"DateTime"`), not `"INT"`, `"DOUBLE"`, `"TEXT"`
  and `"TIMESTAMP"`.
- A field naming one column has `expression` and no `sql`; other `sql` becomes its dialect's `expression` entry.
- Dumps, `model_fields` and class names follow the Ossie vocabulary, so dump shapes and hashes of them change.
- `parse_expr` trees hold `NamedArg`, `DateTrunc`, `Cast` and `TemporalLiteral` nodes; only `parse_filter_expr`
  projects them onto the 1.x shapes.
- Drift reason texts changed, and a field whose `filter` reads a dropped field is dropped too.
- An ARRAY field also allows `count_distinct`, and an aggregate over a joined dataset no longer associates with the
  population's grain (`count_distinct(customers.email)` by `orders.status` counts per status).
- Stored files carry the current `version`: upgrade 1.x files with `slayer storage upgrade` or `upgrade_datasets`
  before a version check.

### MCP, CLI and environment

**The MCP `inspect_model` tool is gone.** Call `inspect` with `entity_type="dataset"` and `compact=False`; without
`compact=False` you get the short view.

```text
inspect(reference="warehouse.orders", entity_type="dataset", compact=False)
```

**`slayer serve --host` applies to the MCP endpoint at `/mcp`.** Bound to a non-loopback address, including the
default `0.0.0.0`, `/mcp` accepts any `Host` header (1.x answered 421 to any non-localhost `Host`); bound to
`127.0.0.1`, `localhost` or `::1` it still refuses non-loopback hosts with 421.

**`--models-dir` is gone from every command**; pass the path to `--storage`: `slayer mcp --storage ./slayer_data`.

**`SLAYER_MODELS_DIR` is silently ignored.** Nothing warns: SLayer starts an empty store in the platform default
directory. Rename the variable to `SLAYER_STORAGE`.

**Cube and dbt imports read the datasource.** `slayer import-cube` and `slayer import-dbt` connect to `--datasource`
when it can be reached and take column types from it; an unreachable datasource still
imports, with a note that types were not checked. On Postgres, Redshift, Snowflake and Oracle datasources, unquoted
mixed-case names are stored in lowercase (`Sales.OrderItems` becomes `sales.orderitems`, column `OrderAmount`
becomes `orderamount`), and a project with such names is refused when `--datasource` is not configured at all.
Constructs the target database cannot run (a MySQL `median`, a `max` over a column of unknown type) are dropped and
listed in the conversion report. Re-import against a configured datasource and update queries that use the old
mixed-case names.

**Ossie export writes `0.3.0.dev0`.** `slayer export-osi` writes `version: 0.3.0.dev0` (1.x wrote `0.2.0.dev0`), so a
consumer that validates exports against the 0.2 schema must move to 0.3.

**Ossie extensions travel under `nonportable_extensions`, with object `data`.** `slayer export-osi` writes the `SLAYER`
payload and other vendors' entries under `nonportable_extensions`, each `data` a JSON object; 1.x wrote
`custom_extensions` with `data` as a JSON string, which the current Ossie schema rejects. `slayer import-osi` still
reads `custom_extensions` from a 1.x export, with an informational report entry, and refuses a document holding an
entry whose `data` is not a JSON object. Entities' extensions are read into `meta["osi_nonportable_extensions"]`
(1.x: `meta["osi_custom_extensions"]`) with object `data`, and stored 1.x datasets upgrade on load.

```yaml
custom_extensions:
  - vendor_name: ACME
    data: '{"k": 1}'
```

```yaml
nonportable_extensions:
  - vendor_name: ACME
    data: {k: 1}
```

### Ossie documents

**`slayer import-osi` stores each document as written instead of converting it.** A valid document becomes a
[semantic model](../concepts/semantic-models.md) of the datasource, stored verbatim (comments included) under
`semantic_models/<datasource>/<name>.yaml` or in the SQLite `semantic_models` table. A current-shape document needs no
reachable datasource; only a legacy `semantic_model` wrapper document is introspected, to declare its source columns as
fields. `--dialect` is gone: drop it. The form of each expression that runs on the datasource is chosen at load, and an
expression with no runnable form is translated in memory, never written back.

```bash
slayer import-osi ./model.yaml --datasource warehouse --dialect SNOWFLAKE   # 1.x
slayer import-osi ./model.yaml --datasource warehouse                       # 2.0
```

**An invalid document is refused, not imported in part.** 1.x skipped bad files and dropped bad entities with a report
entry; 2.0 refuses the whole document with every reason, stores the other files, and exits non-zero. An entity SLayer
cannot evaluate yet (a window function, for instance) is stored and reported, and fails only when a query reads it.
Validity follows Ossie's own validator: portable `sql` may not use `INTERVAL`, an empty `IN ()`, an alias, a
`DISTINCT` without an argument, or (in a field) an aggregate without `OVER`, all of which 1.x imported. Write date
arithmetic with `DATEADD`, and move a field's aggregate into a metric:

```yaml
expression: {sql: "order_date + INTERVAL '7 days'"}   # 1.x
expression: {sql: "DATEADD(day, 7, order_date)"}      # 2.0
```

**A document repeating a mapping key no longer loads.** 1.x kept the last of two equal keys; 2.0 refuses the document
at import, save and edit, and a stored one is unloadable, naming every repeated key with its line. Keep one:

```yaml
fields:
  - name: amount
    expression: {sql: amount}
    expression: {sql: amount * 2}   # 1.x: silently kept; 2.0: "line 4: duplicate key 'expression'"
```

```yaml
fields:
  - name: amount
    expression: {sql: amount * 2}
```

**Model-level metrics are queried by bare name.** 1.x attached each top-level metric to an anchor dataset; 2.0 keeps it
as a model-scoped metric of the datasource:

```json
{"population": "orders", "metrics": ["orders.revenue_per_customer"]}
```

```json
{"metrics": ["revenue_per_customer"]}
```

**Re-import a 1.x-imported document to upgrade it.** Importing the same document again replaces the datasets 1.x
converted from it: anchored metrics move into the document scope (the report lists each move), SLayer-only settings you
added to those datasets are carried into `SLAYER` entries, and dataset names stay, so saved queries and memories keep
resolving. Nothing migrates on load: 1.x-converted datasets keep loading unchanged until you re-import. Semantic models
live in their own directory or table, so deleting them leaves standalone datasets intact.

**`slayer export-osi` writes one document per datasource.** It merges every semantic model and standalone dataset of
the datasource into one document, which re-imports split back into the same pieces; a datasource holding exactly one
semantic model and no standalone dataset exports that document's stored text unchanged. A model-scoped metric's
reference to a dataset metric is written `AGG(dataset.metric)` rather than expanded.

**Relationship shapes Ossie allows now load for every dataset.** A relationship to its own dataset saves and loads but
takes no part in paths (spelling a hop over it fails); a relationship may be named like a dataset, and a path segment
naming both an edge and another edge's target fails as ambiguous; relationship keys may be computed fields.

**`OsiToSlayerConverter` and `slayer.osi.converter` are gone.** Import from Python with
`slayer.osi.importer.import_osi`:

```python
result = await import_osi(storage=storage, path="model.yaml", data_source="warehouse", engine=engine)
```

### The Ossie vocabulary

SLayer now names things the way Ossie does:

| 1.x | 2.0 |
| -- | -- |
| model | dataset |
| column (of a model) | field |
| measure | metric |
| join (a declared edge) | relationship |
| formula | expression |

Old spellings of input still work until 3.0 ([Part 2](#the-ossie-vocabulary-old-spellings)). These change outright:

**MCP tools are renamed, and the old names are gone.**

| 1.x | 2.0 |
| -- | -- |
| `models_summary` | `datasets_summary` |
| `create_model` | `create_dataset` |
| `edit_model` | `edit_dataset` |
| `delete_model` | `delete_dataset` |
| `validate_models` | `validate_datasets` |
| `recommend_root_model` | `recommend_population` |
| `ingest_datasource_models` | `ingest_datasource` |

**Output uses the new words.** A query response lists metric metadata under `attributes.metrics`, and carries no
`attributes.measures`. Search hits, `inspect` JSON and `datasets_summary` JSON name kinds and sections `dataset`,
`field`, `metric` and `relationships`. Warning payloads follow suit: the kinds `extension_column_inlined` and
`spine_join_dropped` are now `extension_field_inlined` and `spine_relationship_dropped`, and payload fields named
`model`, `column`, `measure`, `measures` or `join` are now `dataset`, `field`, `metric`, `metrics` and `relationship`.
A serialized time dimension names its field under `field`, and an order item under `field`.

**The `slayer import-cube` report category `segment_as_column` is now `segment_as_field`**
(`CubeIssueCategory.SEGMENT_AS_FIELD`); a 1.x report file holding the old value no longer loads into
`CubeConversionResult`.

**Datasets and queries take Ossie's shapes**, and a dump writes only them (old spellings still convert,
[Part 2](#the-ossie-vocabulary-old-spellings)):

- a query metric entry is a string or `{"metric", "alias"}` (with optional `label`, `description`, `datatype`,
  `meta`), and a dimension entry a string or `{"field", "alias"}` (with an optional `label`); an entry without
  `alias` or `label` dumps as its string;
- a time dimension names its result `alias`, an order item's `field` is text, and a query extension names its target
  `dataset`;
- `filter` is a string or a list of strings, dumped as written; a refinement appends its conditions;
- a relationship carries parallel `from_columns` / `to_columns` lists, kept in the order written;
- `datatype` and `element_type` take Ossie's names, `String`, `Integer`, `Decimal`, `Float`, `Boolean`, `Date`,
  `Time`, `DateTime`, `DateTimeTz` and `Opaque`, plus `Array`, matched by exact case and kept as written; `Decimal` and
  `Float` behave as 1.x `DOUBLE`, `DateTime` and `DateTimeTz` as `TIMESTAMP`, and `Time` and `Opaque` as `UNKNOWN`. A
  list shows as `Array<String>`.

**A dataset refuses keys SLayer does not read.** A fresh dataset carrying one, on itself or a field, metric,
relationship, aggregation or aggregation parameter, is refused with an `UnknownKeyError` naming the key, its path and
the dataset, after any old spelling converts; this includes Ossie keys SLayer does not read yet (`ai_context`,
`unique_keys`, …). A stored dataset drops such keys on load, with one `unknown_stored_key` warning naming the dataset
and every dropped path; the next save persists it without them.

**A query refuses keys SLayer does not read.** A query, a refinement, or one of their dimension, metric, time
dimension, order or extension entries carrying an unknown key is refused with an `UnknownKeyError` naming the key, its
location and the keys the object takes (REST answers 422). 1.x silently dropped such a key on a time dimension, so a
Cube-style `dateRange` ran without its date filter. A camelCase spelling of a key the object takes (`dateRange`,
`timeDimensions`, `sourceModel`) is read as its snake_case key; giving both spellings is a conflict. Cube's
`compareDateRange` is refused: compare periods with `change`, `change_pct` or `time_shift`. A stored query follows the
same rules: one holding `dateRange` now applies the range, and one holding any other unknown key fails to load with
the error while the rest of the store loads.

**Query objects validate assignments.** Assigning an attribute of a query, refinement or entry after construction
runs the checks construction runs; a failed assignment raises and leaves the object unchanged.

**A declared Ossie `datatype` is the field's type**, and is no longer recorded in `meta["osi_datatype"]`; a stored
`osi_datatype` folds into `datatype` when it names a value of the stored type's kind. A semantic-model field without a
`datatype` is typed from the live column at query time.

**`slayer export-osi` writes the `SLAYER` extension payload as version 3**, a field's definition under `expression`.
Versions 1 and 2 are still read, a field `sql` there converting with the datasource's dialect.

**Each join exports as its own relationship.** An earlier export merged joins on the same keys into one relationship
whose `SLAYER` entry declared several; loading such an entry now gives one many-to-one relationship, with a load
warning on `inspect`. To restore every join, export again from the source datasource and import that document.

**A 2.0 store cannot be read by 1.x.** Stored datasets, queries, memories and embeddings move to the new keys the first
time 2.0 loads them.

### Installation

- `motley-slayer[postgres]` installs only psycopg, and `[mysql]` only pymysql; `[all]` drops psycopg2-binary, asyncpg
  and aiomysql. A connection string naming `+psycopg2`, `+asyncpg` or `+aiomysql` needs that driver installed
  directly: `pip install 'motley-slayer[postgres]' asyncpg`.
- SQLAlchemy 2.0.43 or newer and pyparsing 3.1 or newer are required.
- mcp `>=2.3,<3` is required (1.x required `mcp<2`), with pydantic 2.12 and uvicorn 0.31.1 or newer.

## Part 2: deprecated in 2.0, removed in 3.0

Each deprecated form still works in 2.x, and using it emits a `FutureWarning` in Python. A deprecated query field
adds a `deprecated_input` warning (`old`, `new`, `removal`) to the response of every query that runs it, dry runs included. A save that
stores it reports it too:
REST dataset saves as that structured object in `warnings`, the MCP `create_dataset` tool as a `Warning:` line in its
reply, the MCP `edit_dataset` tool and REST and MCP memory saves as a message string in `warnings`, and a Python
`engine.save_dataset(dataset, warnings_out=notes)` call by appending the object to `notes`. What is stored is always the replacement.
The `slayer` CLI prints each deprecation as one line per command, however many of these channels carry it; JSON output (`slayer search --format json`) still keeps it in its `warnings`.

**`strict`.** A query carrying `strict` is converted: `strict: true` becomes `to_many_handling: "error"`, and
`strict: false` is dropped. An explicit `to_many_handling` wins. 1.x refused `strict` on new queries; stored queries
that carry it upgrade silently.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "dimensions": ["status"], "measures": ["sum(customers.spend)"], "strict": true}
```

```json
{"population": "orders", "dimensions": ["orders.status"], "metrics": ["sum(customers.spend)"], "to_many_handling": "error"}
```

**`to_many_handling: "broadcast"`.** It still repeats each aggregate at the part of the grain its dataset determines, with a `deprecated_input` warning on
every run; a save stores `"broadcast"` as given. The query JSON schemas, and so the MCP `query` tool's, list only
`associate` and `error`. Give each aggregate `partition_by=` with the dimensions its dataset determines (`[]` for the
grand total); the `broadcast` warning names that `partition_by=`.

```json
{"population": "orders", "dimensions": ["orders.status"], "metrics": ["sum(customers.spend)"], "to_many_handling": "broadcast"}
```

```json
{"population": "orders", "dimensions": ["orders.status"], "metrics": ["sum(customers.spend, partition_by=[])"]}
```

**An extension object in `source_model`.** A query whose `source_model` is an extension object (`{"source_name": …}`)
is converted to `population` naming that dataset plus the object as its one `extensions` entry. 1.x accepted this form;
stored queries that carry it upgrade silently.

<!-- docs-guard: skip -->
```json
{"source_model": {"source_name": "orders", "measures": [{"name": "n_orders", "formula": "count(*)"}]}, "measures": ["n_orders"]}
```

```json
{"population": "orders", "extensions": [{"dataset": "orders", "metrics": [{"name": "n_orders", "expression": "count(*)"}]}], "metrics": ["orders.n_orders"]}
```

**Python-style spellings.** `==`, `is None`, `is not None`, bare `None`, a `[...]` list after `IN` and the
method-call form `customers.max(spend)` keep their meaning. A query using one carries a `deprecated_spelling` warning
(`spelling`, `written`, `canonical`, `removal`) for each. A dataset save reports these warnings the way it reports a
deprecated field, and stores the canonical spelling.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "filters": ["status == 'paid'", "shipped_at is not None", "status IN ['paid', 'open']"], "measures": ["customers.max(spend)"]}
```

```json
{"population": "orders", "filter": ["orders.status = 'paid'", "orders.shipped_at IS NOT NULL", "orders.status IN ('paid', 'open')"], "metrics": ["max(customers.spend)"]}
```

**A field's `sql`.** A field carrying `sql` converts to `expression` (see Part 1); `sql` beside `expression` is refused.

<!-- docs-guard: skip -->
```json
{"name": "net", "sql": "amount - discount"}
```

```json
{"name": "net", "expression": {"dialects": [{"dialect": "DUCKDB", "expression": "amount - discount"}]}}
```

### Root-relative references

In a query that names its population, a 1.x root-relative reference converts to its qualified twin and reports a
deprecation: a bare name reads the population's field or metric where 1.x did (inside an entry, its field, then its
metric, then another entry's alias; in a filter or order, its field, then an alias, then its metric), `count(*)` counts
the population, and a path starting at a relationship or list field of the population gets the population in front. A path
starting at a dataset never converts. A query without a population converts nothing. Saves store the twin.

<!-- docs-guard: skip -->
```json
{"population": "orders", "dimensions": ["status", "buyer.region"], "metrics": ["count(*)", "sum(amount)", "total_revenue"]}
```

```json
{"population": "orders", "dimensions": ["orders.status", "orders.buyer.region"], "metrics": ["count(orders.*)", "sum(orders.amount)", "orders.total_revenue"]}
```

A path starting at a list field converts the same way: `count(skills.*)` from `contractors` becomes
`count(contractors.skills.*)`.

### The Ossie vocabulary: old spellings

Every pre-2.0 spelling below converts to its replacement and reports a deprecation, as described at the top of this
part. Spelling one thing both ways in one object (`measures` and `metrics` in one dataset) is refused with a
`SpellingConflictError`. Stored documents convert silently.

**Dataset keys.**

<!-- docs-guard: skip -->
```json
{"name": "orders", "sql_table": "orders", "columns": [{"name": "amount", "sql": "amount", "type": "DOUBLE"}],
 "measures": [{"name": "revenue", "formula": "sum(amount)"}],
 "joins": [{"target_model": "customers", "join_pairs": [["customer_id", "id"]]}]}
```

```json
{"name": "orders", "sql_table": "orders", "fields": [{"name": "amount", "sql": "amount", "datatype": "Float"}],
 "metrics": [{"name": "revenue", "expression": "sum(amount)"}],
 "relationships": [{"to": "customers", "from_columns": ["customer_id"], "to_columns": ["id"]}]}
```

A metric's and a field's `type` is `datatype`, an aggregation's `formula` is `expression`, and a relationship's
`join_pairs` are its `from_columns` and `to_columns`, in pair order.

**Datatype values.** `TEXT`, `INT`, `BOOLEAN`, `DATE`, `UNKNOWN` and `ARRAY`, and the lowercase `string`,
`integer`, `boolean`, `date` and `unknown`, become `String`, `Integer`, `Boolean`, `Date`, `Opaque` and `Array`.
`DOUBLE` and `number` become `Decimal` when the field's `db_type` is an exact numeric (`NUMERIC(18, 2)`), else `Float`;
`TIMESTAMP` and lowercase `time` become `DateTimeTz` when the `db_type` carries a time zone (`TIMESTAMPTZ`), else
`DateTime`. A metric or list element has no `db_type`, so it takes `Float` or `DateTime`. `Time` with a capital is
Ossie's opaque time-of-day type.

**Query keys**, in every stage, nested query and refinement and in a REST query request.

<!-- docs-guard: skip -->
```json
{"source_model": "orders", "measures": [{"formula": "sum(amount)", "name": "total"}], "filters": ["status = 'paid'"],
 "time_dimensions": [{"dimension": "ordered_at", "granularity": "month"}], "order": [{"column": "total"}]}
```

```json
{"population": "orders", "metrics": [{"metric": "sum(orders.amount)", "alias": "total"}], "filter": ["orders.status = 'paid'"],
 "time_dimensions": [{"field": "orders.ordered_at", "granularity": "month"}], "order": [{"field": "total"}]}
```

A metric entry's `formula` and `name` are `metric` and `alias`. A dimension entry `{"name": "region", "model":
"customers"}` is `"customers.region"`, and a computed dimension's `expression` and `name` are `field` and `alias`. A
time dimension's `dimension` or `column`, and an order item's `column`, are `field`, a reference object there becoming
its dotted text. An order item's `raw_formula` is `raw_expression`, and a query extension's `source_name`, `measures`
and `joins` are `dataset`, `metrics` and `relationships`.

`deprecated_input` warning wherever its response carries `warnings`.

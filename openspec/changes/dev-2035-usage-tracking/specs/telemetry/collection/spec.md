## Purpose

Defines when SLayer records usage telemetry and exactly what a usage report may contain, so that no user content can ever leave the machine.

## ADDED Requirements

### Requirement: Telemetry is active only in processes started by the slayer CLI
SLayer SHALL record, notify and send usage telemetry only in processes started through the `slayer` command-line entry point (`slayer <command>`, `python -m slayer`). Using SLayer as a library — the query engine, the Python client, or an app/server object built from user code — SHALL record nothing, write no telemetry file, print no notice and make no telemetry network request.

#### Scenario: Library use records nothing
- **WHEN** user code builds the query engine, the REST app or the MCP server object and runs queries without the `slayer` CLI
- **THEN** no telemetry file is created, no notice is printed, and no telemetry request is made

#### Scenario: CLI use records
- **WHEN** `slayer query ...` runs with telemetry enabled
- **THEN** the `cli` usage counter for the `query` command increments

### Requirement: A usage report carries only SLayer-defined vocabulary
Every value in a usage report SHALL be a version string, a SLayer-defined enum token, a boolean, a bucket label, a date, a random identifier generated by telemetry, or a count keyed by such a token. Any value not in SLayer's vocabulary SHALL be reported as `other` (or `custom` for user-defined aggregations and transforms). A report SHALL NOT contain SQL, model / column / datasource / memory names or text, filter or formula text, tool or command arguments, error messages, stack traces, file paths, hostnames or IP addresses, and SHALL NOT contain any value hashed or otherwise derived from them.

#### Scenario: Hostile user strings never appear
- **WHEN** queries, models, datasources, memories, MCP arguments, CLI arguments, error messages and the MCP client name contain a sentinel string (including hostile Unicode and very long values)
- **THEN** the serialized report contains neither the sentinel nor any value derived from it

#### Scenario: Unknown exception class
- **WHEN** a counted action fails with an exception class absent from the fixed error table
- **THEN** the failure is counted under the error token `other`

#### Scenario: Error message is never sent
- **WHEN** a counted action fails with a message containing SQL or a table name
- **THEN** only the action's error token is counted

### Requirement: Usage counters per surface
A usage report SHALL count actions per surface as `{ok, errors: {error_token: n}}`, keyed by a fixed token per action:
- CLI: one fixed token per leaf command, never built from argument values; argument-parse errors and help output are not counted.
- MCP: one count per tool call, keyed by tool name.
- REST: one count per request, keyed by the matched route template; unmatched requests and mounts map to fixed tokens; requests to the mounted MCP endpoint are counted as MCP, not REST.
- Flight SQL: one count per executed query (data fetch); schema validation or prepared-statement creation alone is not counted.
- PostgreSQL wire: one count per executed statement, including each statement of a multi-statement message and each execution of a prepared statement; probe and catalog queries map to their own fixed token.

#### Scenario: CLI parse error not counted
- **WHEN** `slayer` is invoked with arguments that fail to parse
- **THEN** no usage counter changes

#### Scenario: Flight query counted once
- **WHEN** a Flight SQL client validates and then fetches one query
- **THEN** the `flight` query counter increments exactly once

#### Scenario: PG multi-statement message
- **WHEN** one PostgreSQL simple-query message holds two statements that both execute
- **THEN** the `pg` query counter increments by two

#### Scenario: Mounted MCP not counted as REST
- **WHEN** a tool call arrives over the MCP endpoint mounted on `slayer serve`
- **THEN** it is counted under `mcp` and not under any REST route

### Requirement: Query feature counters
For each query about to execute, a usage report SHALL count structural flags — multistage, inline source model or model extension, time dimensions, filters, computed dimensions, saved-query reference, non-default `to_many_handling` — and the occurrences of each built-in transform and aggregation name. A name that is not built in SHALL be counted as `custom`. Features SHALL be counted per attempted query, independently of its success.

#### Scenario: Built-in and custom names
- **WHEN** a query uses `time_shift`, `sum` and a user-defined aggregation
- **THEN** the report counts `time_shift` and `sum` by name and the user-defined one as `custom`

#### Scenario: Multistage flag
- **WHEN** a query list of three stages executes
- **THEN** the `multistage` flag count increments once

### Requirement: Environment and context fields
A usage report SHALL include the SLayer version, Python `major.minor`, OS family, CPU architecture, whether the process runs in a container, and which optional extras are installed (determined from package metadata without importing them). It SHALL include queries per dialect, datasources per dialect bucketed (0 / 1 / 2–5 / 6+), and per-process histograms of storage backend type, model-count bucket (0 / 1–10 / 11–50 / 51–200 / 200+) and whether the bundled demo datasource is in use. These values SHALL be taken only from objects the process has already loaded; telemetry SHALL NOT itself open a connection, call storage or import an optional package.

#### Scenario: Model count is bucketed
- **WHEN** the loaded storage holds 37 models
- **THEN** the report records the bucket `11-50`, not the number

#### Scenario: No extra storage access
- **WHEN** a server starts with telemetry enabled
- **THEN** telemetry makes no storage call or database connection of its own

### Requirement: MCP client identification
For each MCP session, a usage report SHALL count the connecting client, mapped from the client's self-reported name against a fixed list of known clients and reported with its major version only. Any other client name SHALL be reported as `other`.

#### Scenario: Known client
- **WHEN** an MCP client identifies as a known client at version `2.3.1`
- **THEN** the session is counted under that client's token with major version `2`

#### Scenario: Unknown client
- **WHEN** an MCP client identifies as `acme-finance-bot`
- **THEN** the session is counted under `other`

### Requirement: Report identity and time resolution
A usage report SHALL carry the install ID, a random batch ID, a schema version, and the first and last calendar dates it covers. It SHALL NOT carry timestamps finer than a date.

#### Scenario: Dates only
- **WHEN** a report covering activity on two days is built
- **THEN** its period holds two dates and no time-of-day values

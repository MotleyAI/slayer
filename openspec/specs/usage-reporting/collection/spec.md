# usage-reporting/collection Specification

## Purpose
Defines when SLayer records usage reporting and exactly what a usage report may contain, so that no user content can ever leave the machine.

## Requirements

### Requirement: Usage reporting is active only in processes started by the slayer CLI
SLayer SHALL record, notify and send usage reporting only in processes started through the `slayer` command-line entry point (`slayer <command>`, `python -m slayer`). Using SLayer as a library — the query engine, the Python client, or an app/server object built from user code — SHALL record nothing, write no usage-reporting file, print no notice and make no usage-reporting network request.

#### Scenario: Library use records nothing
- **WHEN** user code builds the query engine, the REST app or the MCP server object and runs queries without the `slayer` CLI
- **THEN** no usage-reporting file is created, no notice is printed, and no usage-reporting request is made

#### Scenario: CLI use records
- **WHEN** `slayer query ...` runs with usage reporting enabled
- **THEN** the `cli` usage counter for the `query` command increments

### Requirement: A usage report carries only SLayer-defined vocabulary
Every value in a usage report SHALL be a version string, a SLayer-defined enum token, a boolean, a bucket label, a date, a random identifier generated by usage reporting, or a count keyed by such a token. Any value not in SLayer's vocabulary SHALL be reported as `other` (or `custom` for user-defined aggregations and transforms). A report SHALL NOT contain SQL, model / column / datasource / memory names or text, filter or formula text, tool or command arguments, error messages, stack traces, file paths, hostnames or IP addresses, and SHALL NOT contain any value hashed or otherwise derived from them.

#### Scenario: Hostile user strings never appear
- **WHEN** queries, models, datasources, memories, MCP arguments, CLI arguments, error messages and the MCP client name contain a sentinel string (including hostile Unicode and very long values)
- **THEN** the serialized report contains neither the sentinel nor any value derived from it

#### Scenario: Unknown exception class
- **WHEN** a counted action fails with an exception class absent from the fixed error table
- **THEN** the failure is counted under the error token `other`

#### Scenario: Error message is never sent
- **WHEN** a counted action fails with a message containing SQL or a table name
- **THEN** only the action's error token is counted

### Requirement: Usage counters per surface
A usage report SHALL count actions per surface as `{ok, errors: {error_token: n}}`, keyed by a fixed token per action:
- CLI: one fixed token per leaf command, never built from argument values; argument-parse errors and help output are not counted; the `slayer usage-reporting` commands are not counted.
- MCP: one count per tool call, keyed by tool name.
- REST: one count per request, keyed by the matched route template; unmatched requests and mounts map to fixed tokens; requests to the mounted MCP endpoint are counted as MCP, not REST.
- Flight SQL: one count per executed query (data fetch); schema validation or prepared-statement creation alone is not counted.
- PostgreSQL wire: one count per executed statement, including each statement of a multi-statement message and each execution of a prepared statement; probe and catalog queries map to their own fixed token.

#### Scenario: CLI parse error not counted
- **WHEN** `slayer` is invoked with arguments that fail to parse
- **THEN** no usage counter changes

#### Scenario: Flight query counted once
- **WHEN** a Flight SQL client validates and then fetches one query
- **THEN** the `flight` query counter increments exactly once

#### Scenario: PG multi-statement message
- **WHEN** one PostgreSQL simple-query message holds two statements that both execute
- **THEN** the `pg` query counter increments by two

#### Scenario: Mounted MCP not counted as REST
- **WHEN** a tool call arrives over the MCP endpoint mounted on `slayer serve`
- **THEN** it is counted under `mcp` and not under any REST route

### Requirement: Query feature counters
For each query about to execute, a usage report SHALL count structural flags — multistage, inline source model or model extension, time dimensions, filters, computed dimensions, saved-query reference, non-default `to_many_handling` — and the occurrences of each built-in transform and aggregation name. A name that is not built in SHALL be counted as `custom`. Features SHALL be counted per attempted query, independently of its success.

#### Scenario: Built-in and custom names
- **WHEN** a query uses `time_shift`, `sum` and a user-defined aggregation
- **THEN** the report counts `time_shift` and `sum` by name and the user-defined one as `custom`

#### Scenario: Multistage flag
- **WHEN** a query list of three stages executes
- **THEN** the `multistage` flag count increments once

### Requirement: Environment and context fields
A usage report SHALL include the SLayer version, Python `major.minor`, OS family, CPU architecture, whether the process runs in a container, and which optional extras are installed (determined from package metadata without importing them). It SHALL include queries per dialect, datasources per dialect bucketed (0 / 1 / 2–5 / 6+), and per-process histograms of storage backend type, model-count bucket (0 / 1–10 / 11–50 / 51–200 / 200+) and whether the bundled demo datasource is in use. These values SHALL be taken only from objects the process has already loaded; usage reporting SHALL NOT itself open a connection, call storage or import an optional package.

#### Scenario: Model count is bucketed
- **WHEN** the loaded storage holds 37 models
- **THEN** the report records the bucket `11-50`, not the number

#### Scenario: No extra storage access
- **WHEN** a server starts with usage reporting enabled
- **THEN** usage reporting makes no storage call or database connection of its own

### Requirement: MCP client identification
For each MCP session, a usage report SHALL count the connecting client, mapped from the client's self-reported name against a fixed list of known clients and reported with its major version only. Any other client name SHALL be reported as `other`.

#### Scenario: Known client
- **WHEN** an MCP client identifies as a known client at version `2.3.1`
- **THEN** the session is counted under that client's token with major version `2`

#### Scenario: Unknown client
- **WHEN** an MCP client identifies as `acme-finance-bot`
- **THEN** the session is counted under `other`

### Requirement: Report identity and time resolution
A usage report SHALL carry the install ID, a random batch ID, the report schema version (2), the first and last calendar dates it covers, and the install's first-successful-query date. It SHALL NOT carry timestamps finer than a date.

#### Scenario: Dates only
- **WHEN** a report covering activity on two days is built
- **THEN** its period holds two dates and no time-of-day values

#### Scenario: Schema version 2
- **WHEN** a report is built
- **THEN** its schema version is 2

### Requirement: A retired usage key counts as its surface's other
Counts recorded under a usage key that a later SLayer version no longer defines (a renamed or removed
command, tool or route) SHALL still be reported after an upgrade: when a stored batch is read, each
such key's counts SHALL be added to its surface's `other` key where that key exists, and SHALL be
dropped on their own where it does not. Every other count in the batch SHALL be reported unchanged; a
retired key SHALL NOT cause a batch to be discarded.

#### Scenario: Counts under a renamed CLI command survive an upgrade
- **WHEN** a batch stored before the upgrade counts 2 successful `cli:search.refresh-samples` runs,
  1 `cli:other` run and 5 `cli:query` runs, and is read by a version where the command is
  `datasources refresh-samples`
- **THEN** the report counts 3 successful `cli:other` runs and 5 `cli:query` runs

#### Scenario: A retired key on a surface without an other key
- **WHEN** a stored batch carries counts under a `pg:` key the current version does not define,
  alongside `pg:query` counts
- **THEN** the unknown key's counts are dropped and the `pg:query` counts are reported

### Requirement: Per-session MCP query outcomes
A usage report SHALL carry a histogram of MCP sessions: each row counts the sessions whose successful and whose failed `query` tool calls fall into a given pair of buckets (`0` / `1` / `2-5` / `6-20` / `21+`). A session SHALL be every MCP client session that makes at least one tool call — the one session of a stdio `slayer mcp` process, and each client session of the MCP endpoint mounted on `slayer serve`. A `query` call SHALL count as successful or failed exactly as it is counted under the `mcp:query` usage counter, except that a dry run SHALL be counted neither way. A session without counted `query` calls SHALL be reported in the `0` / `0` row. Each session SHALL be reported exactly once, with its totals, in the counters its process spools when it ends; a send made while the process runs SHALL NOT include it. A forked child SHALL start without sessions. Sessions in equal bucket pairs SHALL be reported as one row, and rows SHALL be ordered by bucket rank.

#### Scenario: Successful and failed queries in one session
- **WHEN** one MCP session makes two `query` calls that succeed and one that fails, then the process ends
- **THEN** the report holds one session row with successful bucket `2-5`, failed bucket `1` and session count 1

#### Scenario: Session without queries
- **WHEN** an MCP session calls only `list_datasources`, then the process ends
- **THEN** the report holds one session row with buckets `0` / `0`

#### Scenario: Sessions with equal buckets share a row
- **WHEN** two MCP sessions on one `slayer serve` each make one successful `query` call and no failing one
- **THEN** the report holds one row with buckets `1` / `0` and session count 2

#### Scenario: Dry run not counted
- **WHEN** an MCP session makes one `query` call with `dry_run` and nothing else
- **THEN** the session is reported with buckets `0` / `0`

#### Scenario: Database failure counted as failed
- **WHEN** a session's `query` call fails in the database
- **THEN** it is counted in the session's failed bucket and under the `mcp:query` errors with a database error token

#### Scenario: Session spanning a send
- **WHEN** a session makes one successful `query` call, a send happens while the process runs, and the session then makes a second successful `query` call before the process ends
- **THEN** the send carries no row for that session, and the counters spooled at process end hold it once with successful bucket `2-5`

#### Scenario: Session totals survive a termination signal
- **WHEN** a `slayer mcp` process whose session made a successful `query` call is stopped by SIGTERM
- **THEN** its spooled counters hold that session with successful bucket `1`

#### Scenario: Forked child does not repeat sessions
- **WHEN** a process with a recorded session forks
- **THEN** the child's counters hold no session rows

### Requirement: First successful query date
A usage report SHALL carry the date of the install's first successful query, or none. A query SHALL count when it succeeds on a query surface — the MCP `query` tool, `slayer query`, the REST `/query` route, a Flight SQL query or a PostgreSQL-wire statement — and is not a dry run; probes and catalog queries SHALL NOT count. The date SHALL be stored with the install ID, set by the first counting query of the current install ID and not changed by later ones, and sent with every report of that install ID. Only a process started by the `slayer` CLI with usage reporting on SHALL set it.

#### Scenario: First successful query sets the date
- **WHEN** no date is stored and a `slayer query` succeeds
- **THEN** the stored date is today and the next report carries it

#### Scenario: Every query surface counts
- **WHEN** no date is stored and the first successful query arrives through MCP, the REST `/query` route, Flight SQL or the PostgreSQL wire
- **THEN** the date is set to today

#### Scenario: Failures, dry runs and probes do not count
- **WHEN** no date is stored and a query fails, a query runs as a dry run, or a Flight SQL or PostgreSQL probe succeeds
- **THEN** no date is stored

#### Scenario: Later queries keep the date
- **WHEN** a date is stored and a later query succeeds on another day
- **THEN** the stored date is unchanged

#### Scenario: Another process rotates the install ID
- **WHEN** a running server has seen the date stored, another process then rotates the install ID, and the server then runs a successful query
- **THEN** the date is stored again for the new install ID

#### Scenario: Library use stores nothing
- **WHEN** user code runs a successful query through the query engine without the `slayer` CLI
- **THEN** no date is stored
